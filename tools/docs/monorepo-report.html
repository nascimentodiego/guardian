Problemas e Soluções em Larga Escala

Desafios que só aparecem quando o número de módulos ultrapassa a centena.

Problema Principal: DI não escala
// Evolução da DI em projetos grandes // Fase 1 (até ~30 módulos) Dagger 2 + kapt // Funciona, mas kapt é lento // Fase 2 (30–100 módulos) Dagger 2 + KSP // ou Hilt // KSP é 2x mais rápido que kapt // Fase 3 (100+ módulos) Anvil (Square) // elimina boilerplate // Fase 4 (Kotlin 2.0 / K2) Metro (Block) // 59% mais rápido // Kotlin-first, compile-time
Affected Modules Detection
// Sem detection: O(n) com módulos PR com 1 arquivo alterado → 20 jobs de CI disparados → 40+ minutos de feedback // Com detection (Bazel query) PR com 1 arquivo alterado → 2 jobs afetados detectados → ~5 minutos de feedback // Economia: ~90% de compute de CI // Usado por: Lyft, Spotify, Google

Comparativo

Monorepo vs Multirepo

✓ Vantagens do Monorepo
✓Refatorações atômicas — uma única PR altera múltiplos módulos consistentemente
✓Ferramentas compartilhadas (lint, CI, convention plugins) aplicadas uniformemente
✓Detecção imediata de quebras entre módulos
✓Sem cerimônia de versionamento entre dependências internas
✓Experiência no IDE melhor: navegação entre módulos sem trocar de projeto
✗ Desvantagens do Monorepo
✗Git clone/fetch fica lento conforme o repo cresce
✗Em 100+ módulos, Gradle puro pode não ser suficiente — requer Bazel/Buck
✗CI precisa ser inteligente (affected targets) para não escalar O(n)
✗IDE pode travar com muitos módulos carregados simultaneamente
✗Controle de acesso granular por time é mais complexo
✓ Vantagens do Multirepo
✓Isolamento total por time/produto
✓Clone e operações git rápidas por repositório
✓Autonomia e ciclos de release completamente independentes
✓Controle de acesso natural — cada time gerencia seu repo
✓Build system padrão (Gradle) funciona bem individualmente
✗ Desvantagens do Multirepo
✗Refatorações cross-repo são dolorosas (múltiplas PRs coordenadas)
✗Dependências compartilhadas propagam lentamente entre repos
✗Duplicação de tooling, CI e convention plugins entre repos
✗Diamond dependency e drift de versões são frequentes
✗Debugging cross-repo é difícil sem Composite Builds

Padrões Universais

O que todas as empresas aprenderam

Independente de monorepo ou multirepo, esses padrões aparecem em todas as empresas que escalaram para 100+ módulos.

01
Escala exige especialização
Todas as empresas com 100+ módulos criaram times dedicados de Developer Infrastructure / Platform Engineering. Não é opcional — é o que permite o resto do time continuar produtivo.
02
Estabilizar antes de modularizar
Lição explícita do Slack: liquidar tech debt e dependências circulares ocultas é pré-requisito. Modularizar código instável multiplica o problema, não o resolve.
03
DI é o maior gargalo
Dagger puro com kapt não escala bem em 100+ módulos. A indústria evoluiu para KSP → Anvil → Metro. Hilt resolve bem até ~100 módulos com KSP.
04
Padrão :api / :impl é universal
Cada módulo de feature expõe apenas interfaces públicas em :api. A :impl é a implementação privada. Outros módulos dependem apenas de :api — garante isolamento e evita dependências circulares.
05
Affected detection é mandatório
Sem detecção de módulos afetados, o CI cresce O(n) com o número de módulos. Com ela, cresce apenas com os módulos alterados. A Lyft economiza ~90% de compute de CI com essa técnica.
06
Monorepo não é bala de prata
O Block documentou os custos após migrar: git lento em repos grandes, IDE strain, testes flaky amplificados. A decisão depende do tamanho do time e do grau de acoplamento entre os produtos.

Arsenal da Indústria Android

Bazel

Build system hermético com remote execution nativo. Melhor para times polyglot (Android + iOS + backend). Curva de aprendizado alta.

bazel.build

LinkedIn, Slack, Dropbox

Build cache distribuído + Predictive Test Selection + Build Scans. Melhor ROI para quem já usa Gradle.

gradle.com/develocity
Metro (Block)
Cash App, Slack

Substituto do Anvil/Dagger para DI compile-time em Kotlin 2.0+. 59% mais rápido que Dagger.

github.com/ZacSweers/metro
Buildkite
Lyft, Shopify, Uber

CI/CD para monorepos com pipelines dinâmicos. Permite gerar jobs em runtime baseado em affected targets.

buildkite.com
Anvil (Square)
Square, Slack — em manutenção

Kotlin compiler plugin que elimina o boilerplate do Dagger em projetos multi-módulo. Em modo de manutenção desde 2023.

github.com/square/anvil
Buck2 (Meta)
Meta, alternativa ao Bazel

Reescrito em Rust. Suporte nativo a Kotlin/Java/Android. Performance excelente, mas ecosistema menor que o Bazel.

buck2.build
Próximos Passos

Roadmap de Evolução do Guardian

O Guardian já está no caminho correto com monorepo + Gradle multi-module. A evolução natural por fase de crescimento.

Agora — Qualquer tamanho Atual
Adotar o padrão :api/:impl nos módulos de feature. Previne acoplamento e dependências circulares que se tornarão dolorosas em escala. Hilt + KSP já é a configuração correta para o tamanho atual.
~30–50 módulos Próximo
Habilitar Gradle Remote Build Cache (Develocity ou self-hosted via GCS/S3). Configuration Cache e Build Cache já estão parcialmente configurados no gradle.properties do projeto — o próximo passo é tornar o cache distribuído.
~100 módulos
Implementar affected modules detection no CI — disparar apenas os jobs de teste/lint dos módulos alterados pelo PR. Reduz feedback de CI de minutos para dezenas de segundos.
200+ módulos
Dedicar um engenheiro a Developer Experience / Build Infrastructure. Avaliar Gradle Predictive Test Selection (Develocity). Considerar plugin de IDE para carregamento seletivo de módulos (padrão Square/Block).
500+ módulos
Reavaliar Bazel vs Gradle com base no perfil do time. Se o codebase for polyglot (Android + iOS + backend), Bazel oferece remote execution nativa. Se for só Android, Gradle + Develocity + affected detection provavelmente ainda é mais rentável.
